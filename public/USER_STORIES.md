See the coverage map in the repository README. Executed results belong in the dedicated host evidence folder, not this source document. The hosted Linux campaign makes one real Chromium checkout with a fictional shopper and one dispatch, then requires a receipt page, order response, cart API result, allowlisted checkout/payment/email span correlation and read-only Valkey snapshot join. These are observations of the simulated pinned demo; OTel spans are not an independent business journal, and the Valkey query only observes cart bytes. For payment-unavailable, missing traces alone do not qualify the result: the harness records one exact checkout dispatch, the HTTP error/no-order response and a successful cart readback; CI additionally requires an exported checkout error span carrying that synthetic shopper ID. An unavailable, stale, malformed, or wrong-shopper readback remains `UNKNOWN` and cannot turn an unsuccessful assessment into an observed result. The pinned Cart service serializes an empty default cart without a `userId`; those readbacks are labeled `NOT_ECHOED_FOR_EMPTY_CART`, not identity-confirmed. Non-empty cart readbacks must echo the requested synthetic shopper. `shared-cart-conflict` uses two sequential clients; neither the actor labels nor client ordering prove application authorization or service-handler overlap. The separate overlap diagnostic preserves measured client intervals and reports overlap observed/not observed, but never claims handler interleaving. CI also stops and restarts the same recorded conflict project and verifies the same cart through the HTTP API before exercising fresh-world reset/replay. This product does not establish settlement, fulfillment, durable deduplication, safe retry, application authorization, external email delivery, or durable behavior across host/daemon loss.
